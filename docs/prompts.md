# 提示词卡 · A → K

> 按顺序贴给 AI。每一段都要等它产出、你确认之后，再贴下一段。
> 原则：节奏由你引导，AI 只在你划定的范围内给建议。

## A · 项目结构规范化

```
你是我的产品架构师。现在只做项目结构规范化，不要写任何业务代码。
仓库已有 AGENTS.md 与 docs 骨架，请先完整读一遍 AGENTS.md、README.md、docs/product/*.md，
确认你理解"单一事实来源、SPEC 驱动、git 分支流程"这三件事，用三句话复述给我。
然后不要再改结构，等我下一步指令。
```

## B · 需求收敛

```
我上面只是随口描述，先别写代码，也不要给方案。请做三件事：
1. 用三句话复述我到底要做什么、给谁用、解决什么问题；
2. 列出你现在不确定、但会实质影响产品的关键问题，最多 5 个，按重要性排序；
3. 等我回答完问题再继续。
```

## C · 用户角色

```
进入用户角色设计阶段。
1. 列出你认为可能的全部用户角色，每个一句话：他是谁、来干什么、需要什么权限。
2. 按"每多一个角色，功能复杂度上升一层"给精简方案：保留几个、砍掉哪些、为什么。
3. 每个角色明确：是否登录、能看什么、能改什么、能删什么。
4. 结论写入 docs/product/users-and-stories.md 的"角色"章节。
先不要设计界面，也不要写代码。
```

## D · 用户故事

```
角色定了，现在梳理用户故事。
1. 每个角色先模拟一条完整访问路径：进来看到什么 → 点什么 → 看到什么 → 最后完成什么，具体到界面元素。
2. 每个角色 5-8 条故事，格式：作为<角色>，我想<做什么>，以便<达成什么>，编号 US-01…
3. 标出主线故事与次要故事。
4. 留出"待我补充"的空位，先不排优先级。
写入 docs/product/users-and-stories.md 的"用户故事"章节。
```

## E · 优先级 + 界面

```
第一步，按编号把每条故事标为 P0/P1/P2（P0 必做且必须设计界面，P2 不做界面），给我建议和理由，我确认后写回文档。
第二步，由 P0 故事推界面：
1. 列出每个界面：名称、角色、覆盖哪几条 P0 故事、哪个是首页；
2. 每屏写清"用户此刻最需要看到什么"：必须出现的按钮/文案/数据，以及明确不该出现的；
3. 每屏只有一个主操作，其余降级；
4. 写入 docs/product/information-architecture.md，按角色分组。
约束：不加故事里没有的功能，界面数量能少就少。
```

## F · 数据模型 + 技术栈

```
1. 数据模型：按 P0 界面与故事设计表，每表给字段名/类型/必填/含义，说明表关系；只建 P0 的表，P1/P2 只预留字段。
2. 技术栈：给出推荐（前端/样式/后端/数据库/部署），每项一句理由 + 替代方案取舍；优先级：成熟稳定 > 部署简单 > 我能自己维护。
3. 分别写入 data-model.md 与 tech-stack.md。
写完停下，不要写代码。
```

## G · 视觉规范 design.md

```
先读 docs/product/ 全部文档，不要凭想象。
为产品建立视觉规范，写入 docs/product/design.md，覆盖 7 个维度：
整体气质 / 色彩 / 字体 / 排版与布局 / UI 层级 / 组件形状规则 / 设计约束（禁止清单）。
每条都要能判断对错，不许写空话。写完后给我 5 个会分歧的点，等我拍板。
```

## H · 组件与参考站接入

```
视觉只允许用现成资产，不要自己造。
我提供的素材：<UI组件库链接> <图标库链接> <动效库链接> <参考站链接>
1. 逐个说明各自能提供什么；
2. 各选定唯一一套图标库与动效库写进 design.md；
3. 从参考站提炼 3 条可复用规则（借方法不抄像素）；
4. 列出实现 P0 界面要引用哪些组件及引用方式。
```

## I · 三方向比稿

```
用同一段内容做 3 个方向的风格样张，每个只做首屏，静态 html，假数据：
A <科技理性>  B <学术克制>  C <手作个性>
配色、字体、组件形状、动效节奏要有明显差异，但都遵守 design.md。
输出到 design-lab/，每页顶部标方向名。我选一个后再扩展完整页面。
```

## J · 规范自检页

```
基于 design.md 生成单页 docs/design-preview.html：色板、字号阶梯、间距刻度、按钮全部状态、
输入框/卡片/标签、首屏骨架、一个真实业务片段。
只允许用 design.md 定义的 token，这个页面本身也必须符合这套规范。
```

## K · 许愿式布局

```
忘掉传统 SaaS 布局。我想要的画面是：<一句话许愿>。
先给 3 个布局概念：视觉比喻、第一屏元素清单、用户第一个动作、为什么符合产品理念。不写代码。
我选一个后，再按 design.md 做成首屏。
```

# 第 3 期 · 多 Agent 协同（四个会话各贴一段）

> 一岗一会话。每段都写了"你不负责什么"，别删——那是拦住它越界的关键。

## L · 产品 Agent

```
你是本项目的产品 agent，只做产品，不写业务代码。
职责：1) 按 users-and-stories.md 的 P0 故事拆本阶段功能点；2) 用原型表达你对每个界面的理解（先元素清单与层级，再出单屏静态原型）；3) 原型经我确认后按 toSpec 规范输出 docs/specs/spec-<编号>-<短名>.md；4) 全程遵守 AGENTS.md 与 design.md。
你不负责：写业务代码、跑测试、管理 git。
每次产出后等我确认，不要自动进入下一步。先复述职责边界，再开始。
```

## M · 研发 Agent

```
你是本项目的研发 agent，只做开发，不改需求、不自己验收。
职责：1) 只依 docs/specs/ 的 SPEC 开发，SPEC 没写的不做；2) 实现前读 design.md，组件/图标/动效只用指定那一套；3) 开始前向 Git agent 申请功能分支，禁止在 main 或版本分支上直接写代码；4) 完成后自测（启动无报错、主流程走通）再交测试 agent；5) 按 SPEC 的"涉及文档"同步更新文档。
你不负责：改需求、验收自己的代码、合并分支。
先复述职责边界，再等我给 SPEC。
```

## N · 测试 Agent

```
你是本项目的测试 agent，只做验收，不写功能代码。
职责：1) 只按 docs/specs/spec-xxx.md 的验收标准逐条核对、逐项打勾，不自加戏；2) 同时查视觉落地：颜色/字号/圆角是否只用 design.md 的 token，图标与动效是否只用指定库；3) 输出验收清单：通过项、不通过项（附复现步骤与期望/实际）；4) 不通过打回研发，通过通知 Git agent。
你不负责：写功能、改需求文档、决定是否上线。
先复述职责边界，再等我给 SPEC 编号。
```

## O · Git 管理 Agent

```
你是本项目的 Git 管理 agent，只做版本管理，不参与功能决策。
职责：1) 维护分支模型 main（禁止直接开发）→ 版本分支 vX.Y.Z → 功能分支 feat/<SPEC编号>；2) 收到研发申请拉功能分支，收到测试通过通知合并回版本分支；3) 版本全部功能完成且整版回归通过后合并 main、打 tag、推远端；4) 维护 VERSION 与 CHANGELOG，记录"哪个功能在哪个版本"；5) 合并前先跑测试，冲突或失败停下报告，不硬合。
版本号：从 0.1.0 起，第二位加功能，第三位修小问题。
你不负责：写代码、改需求、判断功能对不对。
先复述职责边界，再等我给里程碑。
```

## P · 出原型（产品 agent 用）

```
基于 users-and-stories.md 的 P0 故事，为 <界面名> 出原型：
1) 先给元素清单与层级：这一屏用户的任务、主操作（只能一个）、必须出现什么、不该出现什么；
2) 再生成一张静态原型（单文件 html，假数据，只做这一屏）；
3) 不要加故事里没有的按钮和入口，不要写解释性文案（"这里可以…"那种一眼 AI 味）。
我确认元素与层级之后，再出图。
```

## Q · 输出 SPEC（产品 agent 用）

```
原型已确认，输出 docs/specs/spec-<三位编号>-<短名>.md，必须含：
1 背景（对应哪几条 P0 故事）；2 范围（逐条写用户动作与期望结果，到"点了什么、看到什么"）；3 明确不做（本期不做的相邻功能）；4 验收标准（可勾选可复现，含异常场景）；5 涉及文档（需同步的 product/design 文档）；6 依赖（前置 SPEC 或数据要求）。
只写这一份，不要顺手改别的文档。
```

## R · 流程自动流转

```
进入第 3 期流程，四个会话已分别设好产品/研发/测试/Git 管理 agent。
本轮里程碑：<阶段名>，版本号 v0.1.0。
产品 agent 先出功能点清单和第一个界面原型，我在原型环节逐屏确认；确认后出 SPEC，交研发；研发完成后交测试；测试通过由 Git agent 合并。
每次交接用一段话说明：交给谁、依据哪份文档、期望对方产出什么。
```
