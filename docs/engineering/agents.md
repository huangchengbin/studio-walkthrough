# 多 Agent 协同开发（第 3 期）

> 四个"员工"，一人一岗；人只在**原型**环节拍板，后面自动流转。
> 工具侧落地：Qoder / 豆包工作 里开 4 个会话，一个会话只承担一种职责。

## 一、角色与边界

| Agent | 负责 | 明确不负责 | 产出 |
|---|---|---|---|
| 产品 agent | 拆功能点、出原型、写 SPEC | 不写代码、不做测试 | 原型图、`docs/specs/spec-xxx.md` |
| 研发 agent | 按 SPEC 开发、自测 | 不改需求、不自己验收 | 代码、变更说明 |
| 测试 agent | 按 SPEC 逐条验收、查视觉落地 | 不写功能代码 | 验收清单、缺陷单 |
| Git 管理 agent | 拉分支、合并、打 tag、回退 | 不参与功能决策 | 分支与版本记录 |

**关键**：每个会话的提示词里必须写清"你不负责什么"。只写"你负责开发"，它迟早顺手把需求也改了。

## 二、开发流程

```
① 产品 agent 出原型 ──► ② 人检查原型 ──► ③ 输出 SPEC ──► ④ 研发开发 ──► ⑤ 测试验收
                            ▲ 不满意打回                              ▲ 不通过打回
                                                                     └─ 通过则合并
```

### ② 人在原型环节看三件事
1. 每个按钮是不是摆在该在的位置
2. 有没有多出来的、不必要的按钮和入口
3. 有没有多余文案 —— 尤其是 AI 爱加的"防御性解释"（"这里可以…"），一眼就是 AI 味

同时确认：**首屏是不是用户此刻最需要的那件事**（布局就是在这步定稿的）。

### ④ 研发要对两份说明书
- 产品的 `docs/specs/spec-xxx.md`：做哪一部分、边界在哪
- 视觉的 `docs/product/design.md`：组件、图标、动效只能用指定的那一套

### ⑤ 测试也对两份
按 SPEC 逐条打勾，另外查视觉落地：颜色/字号/圆角是否只用 token，图标动效是否只用规定库。

## 三、分支模型

```
main（永远可运行，禁止直接开发）
 └── v0.1.0（版本分支 = 一个里程碑）
      ├── feat/spec-001（功能分支）
      │    开发 → 自测 → 测试验收 → 合并回 v0.1.0
      ├── feat/spec-002 …
      └── 全部完成 → 版本分支整版回归 → 合并 main → 打 tag
```

版本号：从 `0.1.0` 起，第二位加功能（0.2.0），第三位修小问题（0.1.1）。
合并 main 是最严肃的动作，等于"这版要上线了"，必须整版回归通过。

## 四、四个会话的启用顺序

1. 建 4 个会话，分别贴入产品/研发/测试/Git 的工作范围提示词（见 `docs/prompts.md` L-O）。
2. 跟产品 agent 确认本轮里程碑 → 版本号 `v0.1.0`。
3. 产品 agent 按 P0 故事拆功能点 → 出第一个界面的原型。
4. 你逐屏检查原型（按钮/文案/首屏），不满意就打回，满意才让它出 SPEC。
5. 把 SPEC 编号给研发 agent；研发找 Git agent 拉功能分支。
6. 研发完成 → 测试 agent 验收 → 不通过打回，通过则 Git agent 合并。
7. 版本全部功能完成 → 整版回归 → 合并 main → 打 tag → 你真人验收。

## 五、常见失误

- 一个会话干两件事 → 它既改需求又自我验收，返工必然。
- 原型没检查就出 SPEC → 后面三步全在错的基础上做。
- 研发直接改 main → 出问题无法回退，也说不清"上次那个功能在哪个版本"。
- SPEC 没写"明确不做" → 研发顺手加功能，验收范围失控。
